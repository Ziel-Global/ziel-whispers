> **How stage moves work (read once):** A task's legal next stages are simply **every transition that points out of its current status** in the workflow editor.
> - **One** outgoing transition → it is **auto-selected** (no dropdown — a simple confirmation, e.g. `unlinked` → `Development`).
> - **Multiple** outgoing transitions → a **dropdown** appears and the **person picks which one actually happened** (nobody else knows).
> - **Zero** outgoing transitions → **no** "I finished this stage" option / stage section appears at all.
> - The app reads this from the database **every time** — nothing is hardcoded. Change a transition in this editor and the task screens follow immediately (we test this in Part 10).

## Part 6: Test the Dependency Warning

**Goal:** Verify the yellow warning banner appears when a task is moved to an `in_progress` or `done` status while its `finish_to_start` dependency is unfinished. The banner names the unfinished predecessor and does **not** block the change (spec 7.8).

> **Note:** Status changes are made only through **Stage Outcome** — during log submission (Part 7) or the standalone **"Move task to next stage"** section in the View Task dialog. There is **no manual status dropdown** in the Edit Task dialog; the spec removes manual status changes entirely (see 5.20).

> **Why does Task B move before Task A is done? (read once):** In this system a dependency is a **warning, not a lock** (spec 7.8) — the app deliberately lets you move a task even when one of its dependencies is unfinished; it just shows a yellow banner. So moving Task B (the dependent task) first, while Task A is still `unlinked`, is **intentional**: it proves the banner appears and still lets the move through. If the system blocked it, we couldn't test the warning at all. In real usage you'd finish Task A first; Part 10 does exactly that and we verify the warning for Task B disappears.
